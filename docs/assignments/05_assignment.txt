HFTM · Projekt · Meilenstein 5
Die Regeln
Neun Schritte. Am Anfang kann niemand gewinnen, am Ende hat dein Spiel Regeln, und du kannst beweisen, dass sie stimmen.

Start
Worum es geht
Dein Spiel läuft über das Netz, man kann klicken, beide Fenster zeigen dasselbe. Nur gewinnen kann niemand. Die Regeln fehlen.

Du könntest sie dort ergänzen, wo dein Server schon prüft. Dagegen spricht etwas, das du gleich selbst siehst: Solange die Regeln im Server stehen, kannst du sie nicht prüfen. Jede Situation bräuchte einen frisch gestarteten Server und die richtigen Klicks in der richtigen Reihenfolge. Die Fälle, in denen Fehler stecken, trifft man beim Klicken nie zufällig.

Also bekommen die Regeln eine eigene Datei.

Der Kern kennt Spielernummern, Felder und Regeln. Kein Netz, keine Fenster.
Nach jedem Schritt kannst du etwas starten und etwas sehen. Wenn ein Schritt nicht das tut, was hier steht, geh nicht weiter. Die Schritte 1 bis 7 bauen das Beispiel Tic-Tac-Toe, Schritt 8 macht daraus dein Spiel.

Bevor du anfängst: Starte Server und zwei Fenster und mach zwei Züge. Der letzte Meilenstein muss laufen.

Schritt 1
spiel.py anlegen
Neue Datei spiel.py. Du schreibst sie nicht neu, du ziehst heraus, was schon da ist: die Konstanten oben in deinem Server, das Brett, die Angabe wer am Zug ist, und die Prüfungen aus ziehen. Dazu kommt die Siegprüfung, die es noch nicht gibt.

"""spiel.py: die Regeln von Tic-Tac-Toe.
Kennt kein Netz, keine Sockets, kein Fenster."""

FELDER = 9
ZEICHEN = {1: "X", 2: "O"}
LINIEN = [(0, 1, 2), (3, 4, 5), (6, 7, 8),
          (0, 3, 6), (1, 4, 7), (2, 5, 8),
          (0, 4, 8), (2, 4, 6)]


class Spiel:
    def __init__(self):
        self.brett = [" "] * FELDER
        self.am_zug = 1
        self.beendet = False
        self.gewinner = None            # beendet und None heisst unentschieden

    def zug_pruefen(self, spieler, feld):
        """Gibt None zurueck, wenn der Zug erlaubt ist, sonst den Grund."""
        if self.beendet:
            return "das Spiel ist beendet"
        if spieler != self.am_zug:
            return "du bist nicht am Zug"
        if type(feld) is not int or not 0 <= feld < FELDER:
            return "Feld ausserhalb des Bretts"
        if self.brett[feld] != " ":
            return "Feld ist besetzt"
        return None

    def zug_ausfuehren(self, spieler, feld):
        """Fuehrt den Zug aus. Wirft ValueError, wenn er nicht erlaubt ist."""
        grund = self.zug_pruefen(spieler, feld)
        if grund is not None:
            raise ValueError(grund)

        self.brett[feld] = ZEICHEN[spieler]

        if self.hat_gewonnen(ZEICHEN[spieler]):
            self.beendet = True
            self.gewinner = spieler
            return
        if " " not in self.brett:
            self.beendet = True
            return

        self.am_zug = 2 if spieler == 1 else 1

    def hat_gewonnen(self, zeichen):
        for a, b, c in LINIEN:
            if self.brett[a] == self.brett[b] == self.brett[c] == zeichen:
                return True
        return False

    def zustand(self):
        return {"board": list(self.brett), "currentPlayer": self.am_zug,
                "finished": self.beendet, "winner": self.gewinner}
Diese Datei hat keine Importe. Kein socket, kein tkinter, kein threading. Das ist die Probe darauf, ob du richtig getrennt hast, und sie ist messbar: python3 -c "import spiel" darf nichts weiter nachziehen.

zug_pruefen gibt None zurück oder einen Satz. Der Satz wandert später unverändert bis in die Statuszeile deines Gegenübers. Formulier ihn so, dass ein Spieler ihn lesen kann.

zug_ausfuehren ruft selbst zug_pruefen auf und wirft eine ValueError. Damit gibt es die Regeln genau einmal, und niemand kann am Prüfen vorbei ausführen.

Der Spielerwechsel steht ganz am Schluss, nach der Siegprüfung und nach der Prüfung auf ein volles Brett. Ist das Spiel vorbei, wird nicht mehr gewechselt.

zustand() liefert list(self.brett), also eine Kopie. Sonst gibst du eine Referenz auf deine eigenen Daten heraus.

$
Keine Ausgabe heisst: läuft.

Schritt 3
Tests schreiben
Was du eben von Hand getippt hast, schreibst du einmal auf. Danach läuft es auf Knopfdruck, immer wieder.

import unittest

from spiel import Spiel


class TestSpiel(unittest.TestCase):

    def test_besetztes_feld_wird_abgewiesen(self):
        s = Spiel()
        s.zug_ausfuehren(1, 4)
        self.assertEqual(s.zug_pruefen(2, 4), "Feld ist besetzt")

    def test_feld_ausserhalb_wird_abgewiesen(self):
        s = Spiel()
        self.assertEqual(s.zug_pruefen(1, 9), "Feld ausserhalb des Bretts")
        self.assertEqual(s.zug_pruefen(1, -1), "Feld ausserhalb des Bretts")

    def test_wahrheitswert_ist_kein_feld(self):
        s = Spiel()
        self.assertEqual(s.zug_pruefen(1, True), "Feld ausserhalb des Bretts")


if __name__ == "__main__":
    unittest.main()
Jede Methode, deren Name mit test_ beginnt, wird einzeln ausgeführt. Jeder Test baut sich sein eigenes Spiel(), damit kann kein Test einen anderen beeinflussen.

assertEqual(a, b) besteht, wenn beide gleich sind. with self.assertRaises(ValueError): dreht es um und besteht nur, wenn im Block wirklich eine ValueError fliegt.

Die Namen sind lang und deutsch, weil du bei einem Fehlschlag zuerst den Namen liest.

Ergänze Tests, bis diese Sorten vorkommen. Zwölf sind eine gute Zahl.

Sorte	Was du behauptest
Anfangszustand	Wer am Zug ist, dass nichts beendet ist
Jede Ablehnung einzeln	nicht am Zug, Feld besetzt, Feld ausserhalb, Spiel beendet
Jede Art zu gewinnen	bei drei mal drei: Reihe, Spalte, beide Diagonalen
Das Ende ohne Sieger	Brett voll, niemand gewinnt
Dass nichts passiert	nach einem abgelehnten Zug ist der Zustand unverändert
Der Fall, den du fürchtest	die Stelle aus Frage 8 deines Vorschlags
Getestet werden die Ränder und die Verbote, nicht der Normalfall. Dass ein freies Feld belegt werden kann, merkst du beim ersten Klick.

Ein Test, der sich lohnt
In Python ist bool eine Unterklasse von int, und brett[True] ist dasselbe wie brett[1].

def test_wahrheitswert_ist_kein_feld(self):
    s = Spiel()
    self.assertEqual(s.zug_pruefen(1, True), "Feld ausserhalb des Bretts")
Dieser Test besteht nur, wenn du type(feld) is not int geschrieben hast. Mit isinstance(feld, int) fällt er durch, und dann könnte ein Client mit {"feld": true} auf Feld 1 setzen.

Die drei Spielregeln sind weg, die Siegprüfung ist dazugekommen, und die Funktion ist trotzdem kürzer.

Zwei Prüfungen bleiben stehen, und das ist kein Versehen. Ob diese Verbindung einen Spieler hat und ob der Gegner schon da ist, sind keine Spielregeln. Am Küchentisch gibt es sie nicht.

str(fehler) holt den Satz aus der Ausnahme, den dein Kern hineingeschrieben hat. Der Server übersetzt nichts, er reicht durch.

Erst der Stand, dann das Ende. Die Clients sollen zuerst den letzten Zug sehen und danach erfahren, dass Schluss ist.

Die Trennlinie, falls du unsicher bist, wo etwas hingehört:

Gehört in den Kern	Bleibt im Server
Ist dieser Spieler am Zug	Hat diese Verbindung einen Spieler
Liegt das Feld auf dem Brett	Ist der Gegner schon da
Ist das Feld frei	Ist das Spiel voll
Hat jemand gewonnen	Fehlt der Name beim Beitritt
Ist das Brett voll	War die Nachricht überhaupt JSON
Was auch beim Spiel am Küchentisch gilt, gehört in den Kern. Was nur gilt, weil zwei Programme über ein Netz reden, bleibt im Server.

Die Sperre bleibt übrigens, wo sie ist. Der Kern weiss nichts von Fäden, und das soll so bleiben. Nur schützt die Sperre jetzt das ganze Spiel-Objekt statt Brett und Zugangabe. Schreib das in den Kommentar.

Schritt 8
Dein eigenes Spiel
Bis hierhin war der Kern Tic-Tac-Toe. Jetzt kommen deine Regeln hinein. Das ist der längste Schritt, und er sieht bei jedem anders aus.

Spiel	Was in deinen Kern gehört
Vier gewinnt	Die Schwerkraft: Ein Zug ist eine Spalte, der Kern sucht die unterste freie Zeile. Siegprüfung in vier Richtungen, auch die Diagonalen.
Memory	Zwei Karten pro Zug. Der Kern merkt sich die erste und vergleicht beim zweiten Aufdecken. Bei einem Paar bleibt derselbe Spieler am Zug, sonst werden beide wieder zugedeckt.
Schiffe versenken	Zwei Phasen. Platzieren mit Prüfung auf Überlappung und Rand, danach Schiessen mit Wasser, Treffer, versenkt.
Minensucher	Das Minenfeld wird einmal erzeugt, dazu je Feld die Zahl der Nachbarminen. Wer eine Mine trifft, bleibt am Zug.
Mühle	Drei Phasen: Setzen, Ziehen, Springen. Dazu die Mühlenerkennung und das Entfernen eines gegnerischen Steins.
Hangman	Ein Buchstabe statt eines Feldes. Der Kern kennt das Wort und gibt nur heraus, welche Stellen offen sind.
Kartenspiel	Der Kern mischt, teilt aus und prüft, ob eine Karte gespielt werden darf. Die Werte kennt nur er.
Rundenbasierter Kampf	Lebenspunkte, Schaden und die Reihenfolge, in der Aktionen ausgewertet werden.
Zufall gehört in den Kern, und er macht Tests schwer
Gemischte Karten, ein ausgelostes Wort, ein erzeugtes Minenfeld: Das gehört in den Kern, nicht in den Server und schon gar nicht in den Client. Nur dann kann ein Client nicht schummeln.

Damit kannst du aber nicht mehr testen, weil jeder Lauf anders ist. Gib deinem Kern im Konstruktor die Möglichkeit, den Zufall festzulegen, etwa Spiel(startwert=42) oder Spiel(karten=["herz7", "pik9"]). Im Betrieb lässt du das weg, im Test setzt du es. Dann ist dein Spiel zufällig und deine Tests sind es nicht.

Verborgene Information
Bisher hat zustand() allen dasselbe geliefert. Sobald dein Kern etwas weiss, das ein Spieler nicht sehen darf, geht das nicht mehr. Gib ihm eine zweite Methode, etwa sicht_fuer(spieler), die aus dem einen echten Zustand die Sicht für genau einen Spieler baut. Der Server ruft sie für jeden Client einzeln auf, statt einmal an alle zu senden.

Das lässt sich testen, und genau so gehört es sich: ein Test, der behauptet, dass in der Sicht für Spieler 1 die Schiffe von Spieler 2 nicht vorkommen.
