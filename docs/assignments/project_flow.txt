1.1 Die Regel, die alles andere nach sich zieht
Der Server ist die Wahrheit. Der Client zeigt an und schickt Wünsche.

Ein Client schickt nie «ich habe auf Feld 4 gesetzt». Er schickt «ich möchte auf Feld 4 setzen». Der Server prüft, entscheidet, ändert den Zustand und teilt allen mit, wie er jetzt aussieht. Der Client zeichnet, was er bekommt — er rechnet den Zustand nie selbst weiter.

Daraus folgen drei Dinge, die im ganzen Projekt gelten:

    Der Client prüft nie eine Regel, ausser um Knöpfe auszugrauen. Der Server prüft immer nochmals.
    Zufall gehört auf den Server. Würfel, gemischte Karten, ausgeloste Wörter.
    Verborgene Information verlässt den Server nicht. Nicht ausgegraut, nicht versteckt, sondern gar nicht gesendet.

Der Fehler, der am teuersten ist

Man baut zuerst den Client fertig, weil man dort etwas sieht, und legt die Spiellogik dorthin. Der Server wird zur Weiterleitungsstelle, die Nachrichten durchreicht. Das funktioniert, solange beide Clients ehrlich sind und niemand die Verbindung verliert. Danach ist es nicht mehr reparierbar, sondern nur noch neu zu schreiben. Der Ablauf unten geht deshalb bewusst vom Kern nach aussen.

Der Echo-Server

import socket

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as horcher:
    horcher.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    horcher.bind(("0.0.0.0", 5000))
    horcher.listen()
    print("warte auf Port 5000 ...")
    sock, adresse = horcher.accept()
    with sock:
        print("verbunden mit", adresse)
        while True:
            daten = sock.recv(1024)
            if not daten:
                break
            print("empfangen:", daten)
            sock.sendall(daten.upper())
    print("Gegenseite hat geschlossen")

AF_INET ist die Adressfamilie, also IPv4. SOCK_STREAM ist TCP: eine Verbindung, die Bytes in der richtigen Reihenfolge und vollständig überträgt.

SO_REUSEADDR erlaubt, den Port sofort wieder zu belegen. Ohne diese Zeile bekommen Sie beim schnellen Neustart minutenlang Address already in use. Sie werden diese Zeile lieben lernen.

bind(("0.0.0.0", 5000)) horcht auf allen Netzwerkkarten. Mit "127.0.0.1" wäre der Server nur vom eigenen Rechner erreichbar — das ist der häufigste Grund dafür, dass der Mitspieler nicht durchkommt.

accept() wartet, bis sich jemand verbindet, und liefert einen zweiten Socket für genau diese Verbindung. Der erste horcht weiter.

recv(1024) liefert bis zu 1024 Bytes. Ein leeres Ergebnis heisst nicht «nichts da», sondern «die Gegenseite hat geschlossen».

Meilenstein M2Der Spielkern, ohne eine Zeile Netz

Jetzt programmieren Sie Ihr Spiel — als gewöhnliche Python-Klasse, die auf einem einzigen Rechner läuft und von Sockets nichts weiss. Am Ende dieses Meilensteins können zwei Personen an einer Tastatur abwechselnd spielen. Das ist kein Zwischenschritt, den man überspringen kann: Alles, was Sie hier nicht prüfen, prüfen Sie später zwischen zwei Rechnern, und dort ist jeder Fehler dreimal so teuer.
Die Form, die sich bewährt hat

Vier Methoden, immer dieselben. Das Beispiel ist Drei gewinnt; ersetzen Sie den Inhalt durch Ihr Spiel, nicht die Form.

"""Spielkern: kennt kein Netz, keine Sockets, keine GUI."""

LINIEN = [(0,1,2),(3,4,5),(6,7,8),(0,3,6),
          (1,4,7),(2,5,8),(0,4,8),(2,4,6)]


class DreiGewinnt:
    def __init__(self):
        self.feld = [" "] * 9
        self.am_zug = "X"
        self.gewinner = None
        self.beendet = False

    def zug_pruefen(self, spieler, index):
        """Gibt None zurueck, wenn der Zug erlaubt ist, sonst einen Grund."""
        if self.beendet:
            return "Das Spiel ist beendet"
        if spieler != self.am_zug:
            return "Sie sind nicht am Zug"
        if type(index) is not int or not 0 <= index <= 8:
            return "Feld ausserhalb des Bretts"
        if self.feld[index] != " ":
            return "Feld ist besetzt"
        return None

    def zug_ausfuehren(self, spieler, index):
        grund = self.zug_pruefen(spieler, index)
        if grund is not None:
            raise ValueError(grund)
        self.feld[index] = spieler
        for a, b, c in LINIEN:
            if self.feld[a] == self.feld[b] == self.feld[c] != " ":
                self.gewinner, self.beendet = spieler, True
                return
        if " " not in self.feld:
            self.beendet = True
            return
        self.am_zug = "O" if spieler == "X" else "X"

    def zustand(self):
        return {"feld": list(self.feld), "am_zug": self.am_zug,
                "beendet": self.beendet, "gewinner": self.gewinner}

zug_pruefen ist von zug_ausfuehren getrennt, weil Sie beides an verschiedenen Stellen brauchen: der Server prüft und führt aus, die Oberfläche will nur wissen, welche Knöpfe sie ausgrauen soll.

Der Grund ist ein Text, kein False. «Feld ist besetzt» kann der Server unverändert an den Client weiterreichen. Ein blosses False hätte man dort nochmals übersetzen müssen.

zustand() liefert eine Kopie – beachten Sie list(self.feld). Sonst reicht der Server eine Referenz auf seine eigenen Daten heraus, und irgendwo ändert jemand daran herum.

Der Spielerwechsel steht am Schluss, nicht am Anfang, und er ist eine Entscheidung, kein Umschalten. Bei Spielen mit Zusatzzug – Punkte und Kästchen – steht hier eine Bedingung.
Warum type(index) is not int und nicht isinstance

In Python ist bool eine Unterklasse von int. isinstance(True, int) ist wahr, und liste[True] ist dasselbe wie liste[1]. Ein Client, der {"typ": "zug", "feld": true} schickt, setzt damit auf Feld 1 — an einer Prüfung vorbei, die man für wasserdicht hielt. Das ist keine Theorie: Genau dieser Zug wurde beim Testen des Beispielservers angenommen, bis die Prüfung auf type(...) is not int umgestellt war. Ein Zeichen, das im Vorbeigehen übersehen wird, und eine Lücke.

Meilenstein M3Das Protokoll

Ein Protokoll ist die Vereinbarung darüber, welche Nachrichten es gibt, wie sie aussehen und wer wann welche schickt. Es entsteht auf Papier, nicht im Code. Der Test dafür, ob es taugt, ist simpel: Eine andere Person liest es und kann danach einen Client für Ihr Spiel schreiben, ohne Ihren Code gesehen zu haben.
3.1 TCP kennt keine Nachrichten

Bevor Sie Nachrichten entwerfen, müssen Sie eine Eigenschaft von TCP kennen, die fast alle unterschätzen. TCP überträgt einen Strom von Bytes. Es gibt keine Grenzen darin. Was Sie in einem sendall abgeschickt haben, kommt nicht zwingend in einem recv an, und zwei Sendungen können in einem einzigen recv zusammen ankommen.

Das folgende Protokoll ist echte Ausgabe, nicht Illustration. Ein Client schickt zuerst zwei vollständige Nachrichten auf einmal, danach eine Nachricht in zwei Hälften:

ein recv() liefert: b'{"typ":"zug","feld":1}\n{"typ":"zug","feld":2}\n'
ein recv() liefert: b'{"typ":"zug","fe'
ein recv() liefert: b'ld":3}\n'

Wer json.loads(sock.recv(1024)) schreibt, hat in der ersten Zeile zwei Nachrichten in einem String und in der zweiten eine halbe. Beides führt zu einem Fehler oder, schlimmer, zu still verlorenen Zügen.
Ein recv ist keine Nachricht. Sie brauchen eine eigene Grenze.
3.2 Zeilen als Grenze

Die einfachste brauchbare Grenze ist das Zeilenende. Jede Nachricht ist ein JSON-Objekt in einer Zeile, abgeschlossen mit \n. Das Format hat einen Namen, JSON Lines, und ist für genau diesen Zweck verbreitet. Es funktioniert, weil JSON innerhalb eines Objekts keine echten Zeilenumbrüche enthalten darf — in Zeichenketten stehen sie als \n geschrieben, nicht als Byte.

"""Gemeinsame Hilfsfunktionen fuer das Zeilenprotokoll (JSON Lines)."""
import json


def sende(sock, nachricht: dict) -> None:
    """Verschickt genau eine Nachricht als eine Zeile."""
    zeile = json.dumps(nachricht, ensure_ascii=False) + "\n"
    sock.sendall(zeile.encode("utf-8"))


def leser(sock):
    """Liefert eine Nachricht nach der anderen, bis die Gegenseite schliesst."""
    datei = sock.makefile("r", encoding="utf-8", newline="\n")
    for zeile in datei:
        zeile = zeile.strip()
        if not zeile:
            continue
        try:
            yield json.loads(zeile)
        except json.JSONDecodeError:
            yield {"typ": "fehler", "grund": "kein gueltiges JSON"}

sock.makefile("r", ...) legt ein Dateiobjekt über den Socket. Damit übernimmt Python das Zusammensetzen der Bytes zu Zeilen — genau das Problem aus 3.1, gelöst von der Standardbibliothek. Die Schleife for zeile in datei endet, wenn die Gegenseite schliesst.

sendall statt send: send darf einen Teil schicken und melden, wie viel es war. sendall wiederholt, bis alles draussen ist. Nehmen Sie immer sendall.

ensure_ascii=False lässt Umlaute als Umlaute stehen statt als \u00e4. Zusammen mit encode("utf-8") und demselben encoding auf der Leseseite ist das durchgehend sauber.

Ungültiges JSON führt nicht zum Absturz, sondern zu einer Nachricht vom Typ fehler. Der Aufrufer entscheidet, was er damit tut. Diese vier Zeilen sind der Unterschied zwischen einem Server, den man mit einem Tastendruck umwirft, und einem, der es nicht merkt.

Drei Entwurfsregeln, die Sie sich sparen können zu lernen, weil sie hier stehen:

    Bei verborgener Information wird pro Empfänger gebaut. Eine Funktion sicht_fuer(spieler) im Spielkern liefert das, was dieser Spieler sehen darf. Der Server ruft sie für jeden Client einzeln auf.

Meilenstein M4Der Server

Hier trifft Block 1 auf das Projekt. Ihr Server bedient mehrere Clients gleichzeitig, jeder in einem eigenen Thread, und alle greifen auf denselben Spielzustand zu. Das ist der geteilte Zustand aus Kapitel 3 des Skripts — diesmal nicht als Kontostand im Beispiel, sondern als Ihr Spielbrett.
Denkpause

Zwei Clients schicken im selben Moment einen Zug. Beide Threads lesen «X ist am Zug», beide finden das Feld frei, beide schreiben. Welcher Endzustand kommt heraus, und welche der drei Möglichkeiten aus Übung 2 des Übungshefts entspricht dem? Beantworten Sie es, bevor Sie weiterlesen.
Der Aufbau

"""Spielserver: ein Thread pro Client, ein Lock um den Spielzustand."""
import socket
import threading

from netz import sende, leser
from spiel import DreiGewinnt

HOST, PORT = "0.0.0.0", 5000

spiel = DreiGewinnt()
sperre = threading.Lock()          # schuetzt spiel und clients
clients = {}                       # zeichen -> socket


def an_alle(nachricht):
    """Aufrufer haelt bereits die Sperre."""
    for sock in list(clients.values()):
        try:
            sende(sock, nachricht)
        except OSError:
            pass


def zustand_senden():
    an_alle({"typ": "zustand", **spiel.zustand()})


def client_bedienen(sock, zeichen):
    try:
        sende(sock, {"typ": "willkommen", "zeichen": zeichen})
        for nachricht in leser(sock):
            if nachricht.get("typ") != "zug":
                sende(sock, {"typ": "abgelehnt", "grund": "unbekannter Typ"})
                continue
            with sperre:                       # kritischer Abschnitt
                if len(clients) < 2:
                    sende(sock, {"typ": "abgelehnt", "grund": "Gegner fehlt"})
                    continue
                try:
                    spiel.zug_ausfuehren(zeichen, nachricht.get("feld"))
                except ValueError as fehler:
                    sende(sock, {"typ": "abgelehnt", "grund": str(fehler)})
                    continue
                zustand_senden()
                if spiel.beendet:
                    an_alle({"typ": "ende", "gewinner": spiel.gewinner})
    finally:
        with sperre:
            clients.pop(zeichen, None)
            an_alle({"typ": "gegner_weg", "zeichen": zeichen})
        sock.close()


def main():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as horcher:
        horcher.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        horcher.bind((HOST, PORT))
        horcher.listen()
        print(f"Server laeuft auf Port {PORT}")
        for zeichen in ("X", "O"):
            sock, adresse = horcher.accept()
            print("verbunden:", adresse, "als", zeichen)
            with sperre:
                clients[zeichen] = sock
            threading.Thread(target=client_bedienen, args=(sock, zeichen),
                             daemon=True).start()
        with sperre:                       # beide sind da, Startzustand verteilen
            zustand_senden()
        threading.Event().wait()


if __name__ == "__main__":
    main()

Was an diesem Code wichtig ist

Der kritische Abschnitt umfasst Prüfen, Ausführen und Senden. Nicht nur das Ausführen. Gäbe die Sperre nach zug_ausfuehren frei und erst danach sähe das Senden, könnten zwei Zustände in falscher Reihenfolge bei den Clients ankommen. Das ist die Antwort auf Übung 6 aus Block 1, angewandt.

Der Kern prüft, nicht der Server. zug_ausfuehren wirft eine ValueError mit einem lesbaren Grund, den der Server unverändert weiterreicht. Der Server enthält keine einzige Spielregel — suchen Sie im Listing nach dem Wort «Linie», es kommt nicht vor.

nachricht.get("feld") statt nachricht["feld"]. Fehlt das Feld, kommt None, und die Prüfung im Kern weist es ab. Mit den eckigen Klammern hätte eine unvollständige Nachricht den Thread beendet.

Das finally ist nicht optional. Egal wie der Client verschwindet – Fenster geschlossen, Kabel gezogen, Absturz – der Eintrag wird entfernt und die Gegenseite erfährt es. Ohne diesen Block bleiben tote Sockets in der Tabelle und der andere Spieler wartet ewig.

daemon=True sorgt dafür, dass diese Threads das Programm nicht am Beenden hindern. threading.Event().wait() hält den Hauptthread schlafend am Leben, ohne Prozessorzeit zu verbrauchen.
Ein Sendevorgang unter der Sperre

Im Listing wird gesendet, während die Sperre gehalten wird. Das ist für ein Spiel dieser Grösse richtig, weil die Reihenfolge der Zustandsnachrichten sonst nicht garantiert ist. Es hat aber einen Preis: Ein Client, der nichts abholt, kann den Sendepuffer füllen, und dann blockiert der Server für alle. In grossen Systemen bekommt jeder Client deshalb eine eigene Warteschlange und einen eigenen Sendethread. Für Ihr Projekt ist das nicht nötig — aber wenn Sie im Bericht erklären können, warum es das in einem grossen System wäre, haben Sie mehr verstanden als der Code zeigt.

Meilenstein M5Konsolenclient und Robustheit

Der Konsolenclient ist nicht der Vorentwurf der Oberfläche, sondern Ihr Werkzeug für den Rest des Projekts. Wenn später etwas nicht geht, ist die erste Frage immer: Geht es in der Konsole? Damit trennen Sie Netzfehler von Anzeigefehlern in zehn Sekunden.

Der Aufbau ist derselbe wie beim Server, nur umgekehrt: ein Thread liest, was hereinkommt, der Hauptthread wartet auf Tastatureingaben.

import socket
import threading
import sys

from netz import sende, leser

HOST, PORT = "127.0.0.1", 5000


def empfangen(sock):
    for n in leser(sock):
        typ = n.get("typ")
        if typ == "willkommen":
            print("Sie spielen", n["zeichen"])
        elif typ == "zustand":
            print(n["feld"], "| am Zug:", n["am_zug"])
        elif typ == "abgelehnt":
            print("abgelehnt:", n["grund"])
        elif typ == "ende":
            print("Ende. Gewinner:", n["gewinner"] or "unentschieden")
    print("Verbindung beendet")


def main():
    with socket.create_connection((HOST, PORT)) as sock:
        threading.Thread(target=empfangen, args=(sock,), daemon=True).start()
        for zeile in sys.stdin:
            zeile = zeile.strip()
            if zeile == "q":
                break
            if zeile:
                sende(sock, {"typ": "zug", "feld": int(zeile)})


if __name__ == "__main__":
    main()

Meilenstein M6Die Oberfläche

GUI-Programmierung hatten Sie nicht. Sie brauchen davon auch nur einen kleinen Teil, und den bekommen Sie hier. Wir nehmen tkinter, weil es Teil der Standardbibliothek ist: nichts zu installieren, auf allen drei Betriebssystemen gleich, und PNG-Bilder kann es seit Tk 8.6 direkt laden.
6.1 Die eine Regel, die Sie einhalten müssen

Eine grafische Oberfläche läuft in einer Schleife, die auf Ereignisse wartet: Mausklick, Tastendruck, Fenster verschoben. Diese Schleife heisst mainloop() und gehört einem Thread — dem Hauptthread. Ihr Netzthread darf sie nicht anfassen.
Nichts aus einem fremden Thread an der Oberfläche ändern. Nie.

Ein Aufruf wie label.config(...) aus dem Netzthread führt zu Fehlern, die sich nicht reproduzieren lassen — genau die Klasse von Fehlern aus Block 1, Kapitel 3. Manchmal läuft es tagelang gut, dann friert das Fenster ein oder das Programm verschwindet ohne Meldung.

Die Lösung ist ein Briefkasten. Der Netzthread legt Nachrichten in eine queue.Queue und fasst sonst nichts an. Die Oberfläche schaut zehnmal pro Sekunde nach, ob etwas darin liegt. Queue ist für genau diesen Zweck gebaut und braucht keine eigene Sperre.

"""Grafischer Client. Der Netzthread schreibt nur in eine Queue,
gezeichnet wird ausschliesslich im Tk-Thread."""
import queue
import socket
import threading
import tkinter as tk

from netz import sende, leser

HOST, PORT = "127.0.0.1", 5000


class Fenster:
    def __init__(self, sock):
        self.sock = sock
        self.posteingang = queue.Queue()
        self.zeichen = None

        self.wurzel = tk.Tk()
        self.wurzel.title("Drei gewinnt")
        self.knoepfe = []
        raster = tk.Frame(self.wurzel)
        raster.pack(padx=10, pady=10)
        for i in range(9):
            b = tk.Button(raster, text=" ", width=4, height=2,
                          font=("Helvetica", 24),
                          command=lambda i=i: self.zug_senden(i))
            b.grid(row=i // 3, column=i % 3)
            self.knoepfe.append(b)
        self.zeile = tk.Label(self.wurzel, text="verbinde ...")
        self.zeile.pack(pady=(0, 8))

        threading.Thread(target=self.empfangen, daemon=True).start()
        self.wurzel.after(100, self.posteingang_leeren)

    # --- Netzthread ---------------------------------------------------
    def empfangen(self):
        for nachricht in leser(self.sock):
            self.posteingang.put(nachricht)
        self.posteingang.put({"typ": "verbindung_weg"})

    # --- Tk-Thread ----------------------------------------------------
    def posteingang_leeren(self):
        while True:
            try:
                n = self.posteingang.get_nowait()
            except queue.Empty:
                break
            self.verarbeiten(n)
        self.wurzel.after(100, self.posteingang_leeren)

    def verarbeiten(self, n):
        typ = n.get("typ")
        if typ == "willkommen":
            self.zeichen = n["zeichen"]
            self.zeile.config(text=f"Sie spielen {self.zeichen}")
        elif typ == "zustand":
            for b, wert in zip(self.knoepfe, n["feld"]):
                b.config(text=wert)
            dran = n["am_zug"] == self.zeichen
            self.zeile.config(text="Sie sind am Zug" if dran
                              else "Gegner ist am Zug")
        elif typ == "abgelehnt":
            self.zeile.config(text="abgelehnt: " + n["grund"])
        elif typ == "ende":
            self.zeile.config(text="Gewinner: " + (n["gewinner"] or "unentschieden"))
        elif typ == "verbindung_weg":
            self.zeile.config(text="Verbindung verloren")

    def zug_senden(self, index):
        try:
            sende(self.sock, {"typ": "zug", "feld": index})
        except OSError:
            self.zeile.config(text="Senden fehlgeschlagen")


def main():
    sock = socket.create_connection((HOST, PORT))
    Fenster(sock).wurzel.mainloop()


if __name__ == "__main__":
    main()

after(100, funktion) lässt Tk die Funktion in 100 Millisekunden aufrufen — einmal. Dass sie sich am Ende selbst wieder anmeldet, macht daraus eine Schleife, die die Oberfläche nicht blockiert.

get_nowait() wirft queue.Empty, statt zu warten. Deshalb die Schleife mit break: Sie leert den Briefkasten vollständig und kehrt sofort zurück.

lambda i=i: ... mit dem Standardwert ist nötig. Ohne i=i merken sich alle neun Knöpfe dieselbe Variable, und alle senden Feld 8. Das ist die klassische Schleifenfalle, und in Oberflächen fällt sie besonders oft auf.

Die Oberfläche kennt keine einzige Spielregel. Sie zeigt an, was der Server schickt, und schickt Wünsche zurück. Mehr nicht.
6.2 Bilder und Texturen

Tk lädt PNG direkt, ohne Zusatzpaket:

bild = tk.PhotoImage(file="bilder/kreuz.png")

Zwei Fallen mit Bildern

Erstens: Wenn Sie das PhotoImage-Objekt nirgends festhalten, räumt Pythons Speicherverwaltung es weg — und der Knopf wird leer, ohne Fehlermeldung. Deshalb die letzte Zeile: Das Bild wird als Attribut am Widget abgelegt und lebt damit so lange wie dieses.

Zweitens: subsample und zoom rechnen nur mit ganzen Faktoren. Aus 64 Pixeln werden 32 oder 21, nicht 40. Erzeugen Sie Ihre Bilder deshalb gleich in der Grösse, die Sie brauchen, oder in einem ganzzahligen Vielfachen davon. Für beliebige Skalierung bräuchten Sie Pillow — ein Zusatzpaket, das Sie für dieses Projekt nicht brauchen sollten.

Für Bildmaterial dürfen und sollen Sie generative Werkzeuge verwenden. Verlangen Sie explizit PNG mit transparentem Hintergrund und eine feste Kantenlänge in Zweierpotenzen, also 64, 128 oder 256 Pixel. Legen Sie alles in bilder/ ab und notieren Sie in README.md, womit es erzeugt wurde. Die Regeln dazu stehen im Kapitel KI im Projekt.
6.3 Wenn Sie mehr wollen als Knöpfe

Ein Raster aus Knöpfen reicht für Drei gewinnt, Vier gewinnt, Kartenspiele und Quiz. Für freies Zeichnen — Linien bei Punkte und Kästchen, Figuren auf einem Raster — nehmen Sie tk.Canvas: Sie zeichnen mit create_line, create_image, create_rectangle und rechnen im Mausereignis die Pixelkoordinaten in Spielfeldkoordinaten um.

Wer eine echte Spielegrafik will, kann stattdessen pygame-ce verwenden. Das kostet eine Installation und eine andere Struktur — dort gibt es keine after-Methode, sondern eine eigene Hauptschleife, in der Sie den Briefkasten pro Bild einmal leeren. Das Muster bleibt dasselbe: Netzthread schreibt in die Queue, Zeichenschleife liest sie. Nehmen Sie es nur, wenn M6 sonst planmässig fertig wäre.
